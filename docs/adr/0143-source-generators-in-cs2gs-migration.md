# ADR-0143: generated code in cs2gs migration — reproduce at build, don't freeze

- **Status**: Proposed
- **Date**: 2026-07-06
- **Phase**: Phase 9 — migration completeness
- **Related**: ADR-0115 (cs2gs migration tool), ADR-0145 (native generator host — reproduces Roslyn generators at build), ADR-0144 (partial types), ADR-0142 (resx codebehind generator — the "reproduce natively in the G# build" precedent), ADR-0138 (construct coverage & gap triage), ADR-0027 (no Roslyn in the compiler), issues [#2201](https://github.com/DavidObando/gsharp/issues/2201), [#2209](https://github.com/DavidObando/gsharp/issues/2209), [#2210](https://github.com/DavidObando/gsharp/issues/2210), [#2211](https://github.com/DavidObando/gsharp/issues/2211)

## Context

`cs2gs migrate` (ADR-0115) translates **hand-written** C# to G# and **skips**
every generated tree — anything under the project's own `obj/`/`bin/`, or
carrying an `<auto-generated>` header (`CSharpProjectLoader.BuildDocuments` →
`HasAutoGeneratedHeader`, emitting `CS2GS0002`). Discovered while migrating the
Oahu corpus: because the generated code is skipped, every symbol it would
produce is missing and references to it fail at the gsc compile stage
(`GS0157`/`GS0159`). Two families dominate `Oahu.UI`:

1. **CommunityToolkit.Mvvm** — `[ObservableProperty]`/`[RelayCommand]` generate
   members *into the user's own `partial` types* (the dominant blocker).
2. **Nerdbank.GitVersioning `ThisAssembly`** — a class of version constants; not
   a Roslyn generator but an MSBuild target that writes a `.cs` into `obj/`.

An earlier draft of this ADR proposed the obvious fix: run the compilation's
generators *inside cs2gs* and translate/freeze their output into the migrated
G#. That predates two things that have since shipped, and it turns out to be the
wrong shape:

- **ADR-0145 (gsgen) now runs Roslyn generators in the G# build itself.** A
  native `.gsproj` that references a generator package resolves and runs the
  generator (via gsgen) before gsc, exactly as C# does. A *migrated* project that
  keeps the package reference, the annotated members' attributes, and the
  `partial` modifier therefore **regenerates those members on every build** — no
  frozen copy required.
- **The G# SDK/gsc already reproduce build-derived facts from project
  properties.** Assembly version/identity attributes are stamped by gsc from the
  values the SDK passes (the resx codebehind generator, ADR-0142, is the
  precedent for reproducing a *file's* generated content natively in the G#
  build rather than translating it).

So the migration does not need to run generators or freeze their output. It
needs to **preserve the inputs that drive regeneration** and **stop dropping the
hand-authored content it currently skips**. This ADR reframes the problem from
"translate generated code" to "reproduce generated code in the migrated
project's own build, and translate only what is genuinely hand-authored."

The ADR-0027 boundary is unaffected: no Roslyn enters the compiler. Generators
run in gsgen (a sibling tool); gsc gains only the small, self-contained
`ThisAssembly` synthesis below.

## Decision

### A. Principle: reproduce at build, don't freeze

cs2gs does **not** run source generators and does **not** translate generated
output into the migrated G#. Every category of generated code is reproduced by
the migrated project's own G# build; cs2gs's job is to (1) translate the
hand-authored source, (2) preserve the project-level inputs that drive
regeneration (package references, attributes, `partial`, version/identity
properties, implicit-using items), and (3) drop the generated artifacts so the
build's fresh output is the single source of truth. The result is faithful,
never stale, and a fraction of the code the freeze approach required.

### B. Roslyn `[Generator]` output → reproduced by gsgen (ADR-0145)

For the MVVM family and every other Roslyn generator, migration relies on the
gsgen build path. cs2gs must only keep the trigger intact, which it already
largely does:

- **Attributes survive.** `[ObservableProperty]`/`[RelayCommand]` translate to
  `@ObservableProperty`/`@RelayCommand` on the migrated member.
- **The augmented type is `partial`.** The translator's `preservePartialParts`
  mode emits a C# `partial` type as a G# `partial` part, so gsgen's generated
  part can augment it (all parts of a partial type must be marked `partial`, or
  gsc raises `GS0475`).
- **The package reference carries into the `.gsproj`**, and the SDK's
  `_GsharpResolveAnalyzers` (ADR-0145 §E) resolves the generator's analyzer
  assets. At build, gsgen's stub projection + `ForAttributeWithMetadataName`
  reproduce the members. (This is exactly the loop ADR-0145's end-to-end test
  proves for `@ObservableProperty`.)

**`GeneratedRegex` partial methods (issues #3086, #4301).** Their trigger is
itself a non-void partial-method definition, so the generic partial-method
elision rule would erase the declaration while value-position calls such as
`Pattern().Match(...)` remain. cs2gs translates the definition to a G#
declaring part (ADR-0192), the same form a native G# project writes:

```gsharp
partial class Patterns {
    shared {
        @GeneratedRegex("\\d+", RegexOptions.IgnoreCase)
        private partial func Digits() Regex;
    }
}
```

A static method goes in the type's `shared` block and an instance method stays
an instance member. The generated C# implementation is dropped like any other
generator output, even when a committed file holds it. At build, gsgen runs
the targeting pack's Regex generator and back-translates its implementation
as the matching implementing part (ADR-0145's 2026-09-24 amendment), so the
migrated project runs the generator's specialized matcher, not a cached
`Regex` constructed by hand. The rules:

- **The attribute** is recognized by its resolved type, never by its spelling
  (an alias works). Its arguments, pattern, options, match timeout and
  culture name, are re-spelled from their constant values, positionally in
  constructor order, so a `const` pattern or a named
  `matchTimeoutMilliseconds:` argument reaches gsgen as a literal, and the
  flags are spelled as enum members.
- **Culture-sensitive IgnoreCase** (a culture name, or an inline `(?i)`
  without `CultureInvariant`) needs no special handling: the real generator
  applies the culture.
- **The entry class.** A C# entry class whose members are all private is
  normally hoisted to top-level funcs, which cannot be partial. An entry class
  that declares a `[GeneratedRegex]` method is kept as a class instead. When
  it is the `Program` class of a top-level-statements program, its private
  members are emitted `internal`: C# top-level statements are the body of
  `Program`'s entry point, but G# top-level statements belong to the
  compiler's own `<Program>` type, and hoisting was no stricter.
- **Unsupported shapes** are reported rather than rewritten: a method of a
  record, record struct or other type that is not a G# class or struct
  (`GS0607`); of a nested type, because gsgen's stub renders only top-level
  types, so no implementing part would be generated (`GS0609`); and in the
  legacy merge mode, whose single merged type is not partial (`GS0608`).
  The partial-property form of `[GeneratedRegex]` is reported too: G# has no
  partial properties (ADR-0192 §F).

*History.* Until 2026-09-25 cs2gs instead emitted one private cached `Regex`
constructed from the bound attribute's pattern, options and timeout, in a
field named `__generatedRegex_<method>`, plus an accessor, and reported
culture-sensitive IgnoreCase as unsupported. Issue #4301 retired it: the
synthesized name broke the no-synthetic-identifiers rule, and the rewrite gave
up the generator's compile-time specialization.

**File/options-driven generators (Avalonia `.axaml`, issue #2223).** Some
generators consume non-source inputs rather than attributes — Avalonia's XAML
name generator reads each `.axaml` (a Roslyn `AdditionalText`) and, guided by
`build_property.AvaloniaNameGeneratorBehavior` +
`build_metadata.AdditionalFiles.SourceItemGroup=AvaloniaXaml`, generates the
partial `InitializeComponent()` and named-control fields into the `.axaml.cs`
code-behind. These reproduce through the same gsgen path once gsgen forwards
`AdditionalText` + `AnalyzerConfigOptions` (ADR-0145 §C, issue #2223). cs2gs
keeps the trigger intact by (a) discovering the project's `@(AdditionalFiles)` +
`.axaml` (`CSharpProjectLoader`), (b) forwarding them — tagged
`SourceItemGroup=AvaloniaXaml` — plus `RootNamespace`/`ProjectDir` options to the
Compile stage's gsc invocation, and (c) preserving the code-behind as its own
partial declaration (the default since issue #3410). The
runtime side (Avalonia's `CompileAvaloniaXaml` IL-rewrite) is a language-agnostic
post-compile MSBuild task that hooks the standard `AfterCompile` chain and needs
no G# changes.

**Pipeline requirement.** The cs2gs Compile stage shells out to gsc directly
(`GscInvoker`, not the SDK), so gsgen does not run there today and the stage
would still see missing symbols. The Compile stage must run gsgen before gsc —
either by building the emitted `.gsproj` through `Gsharp.NET.Sdk` (which runs
gsgen) or by invoking the `gsgen` CLI to produce the `.g.gs` and passing them
alongside the user `.gs` — so validation matches the project's real build.

### C. `ThisAssembly` and version constants → synthesized by the G# build

Instead of translating Nerdbank.GitVersioning's `obj/ThisAssembly.cs`, the G#
build **synthesizes** the `ThisAssembly` type from the version/identity facts it
already receives (gsc is passed the assembly version by the SDK's build task;
this extends that to the small set of `ThisAssembly` constants —
`AssemblyVersion`, `AssemblyFileVersion`, `AssemblyInformationalVersion`, and
peers — sourced from the build's version inputs, e.g. `version.json`). This
mirrors ADR-0142's resx codebehind generator: a build-derived file is
reproduced natively in the G# build rather than frozen at migration. cs2gs drops
the generated `ThisAssembly.cs`; references to `ThisAssembly.*` resolve at build
time and stay correct across commits (a frozen copy would go stale every
commit).

### D. SDK-derived non-type files → reproduced from project properties

`AssemblyInfo.cs` (assembly identity/version attributes) and `GlobalUsings.g.cs`
(implicit global usings) are generated by the .NET SDK from project properties —
`<Version>`/`<AssemblyTitle>`/… and `ImplicitUsings`/`<Using>` items. cs2gs
preserves those properties/items in the emitted `.gsproj` and drops the
generated files; the G# SDK/gsc reproduce the equivalent assembly attributes and
global imports. Nothing is translated or frozen for these.

### E. Classify by provenance, not by type-content — and translate the
hand-authored non-type source cs2gs currently drops

The blanket skip is replaced by a single question per generated candidate:
**does the migrated project's build reproduce this file?**

- **Reproduced by the build** → *drop it* (with an informational `CS2GS0002`):
  Roslyn-generator output (§B), synthesized `ThisAssembly` (§C), SDK-derived
  `AssemblyInfo`/`GlobalUsings` (§D). No frozen copy.
- **Hand-authored** → *translate it*, **including files that declare no types**.
  The current "generated" heuristic over-collects: a hand-written source that
  carries only *assembly-level* content — `[assembly: InternalsVisibleTo(...)]`,
  custom assembly attributes, hand-written `global using` directives — declares
  no type and is silently dropped today, losing real semantics. cs2gs must
  translate this content: assembly-level attributes → G# assembly-level
  annotations (G# already has the surface — `CompilationUnitSyntax.AssemblyAttributes`
  / `ParseFileLevelAssemblyAttributes`), hand-written global usings → G#
  `import`s. So this is a translator/classification change, not a new
  language feature. The axis that matters is **provenance (reproducible-by-build vs.
  hand-authored)**, not whether the file happens to declare a type — the old
  type-declares gate conflated a generated `GlobalUsings.g.cs` (drop) with a
  hand-written `AssemblyAttributes.cs` (translate).

The resx carve-out is unchanged: a `Resources.Designer.*` is owned by ADR-0142's
resx generation path and is dropped here so the two don't collide.

### F. Provenance, triage, and determinism

- **Provenance for the residue.** Any generated file that is *neither*
  reproduced by the build *nor* hand-authored — an exotic MSBuild-emitted
  `Compile` item, a T4 template output with no G# equivalent — is reported (a
  `CS2GS0004`-class triage artifact, ADR-0138) so it surfaces rather than
  vanishing. These are, by definition, tool/SDK gaps (the user cannot edit the
  source), and the triage note says so.
- **gsgen fidelity is where the real gaps now live.** Because migration relies
  on gsgen to reproduce Roslyn output, the quality of that back-translation is
  the gating factor. The known gaps against real MVVM output are already filed:
  gsc static access through a fully-qualified generic type
  ([#2209](https://github.com/DavidObando/gsharp/issues/2209)), gsc unqualified
  calls to inherited imported-base members
  ([#2210](https://github.com/DavidObando/gsharp/issues/2210)), and cs2gs/gsgen
  import synthesis for generator output
  ([#2211](https://github.com/DavidObando/gsharp/issues/2211)). Fixing these
  benefits native builds and migration identically.
- **Determinism** is inherent: reproduction runs the real generator / the SDK's
  own derivation on every build, so the migrated project is byte-stable per its
  inputs without cs2gs freezing anything.

### Amendment (2026-09-23): hand-authored partial methods → G# partial methods

This ADR's translator rule for C# partial methods was written when G# had none:
an unimplemented partial method is elided together with its call sites, and an
implemented pair translates only its implementation, as an ordinary method
(the definition node yields nothing — which also silently dropped attributes
written only on the definition). ADR-0192 has since given G# partial methods
(`partial func F(...) R;` + `partial func F(...) R { … }`), so the rule is now:

- **Implemented pair, both parts hand-authored → a G# declaring part plus
  implementing part**, each in the G# `partial` type part of its own C# file,
  each carrying its own method-level attributes (gsc unions them). Each part
  is spelled in its own file (the declaring part under the definition file's
  scope), but both are built from the implementation's symbol, so the facts
  only the implementation knows — `async` (which C# lets only the
  implementation say), iterator and suspend unwrapping, nullability promotion
  — are the same on both. Parameter defaults are the definition's (the ones C#
  callers see) and parameter attributes are the union of both C# parts' (C#'s
  own rule), emitted identically on both parts.
- **Pairs are opt-in and reconciled after translation.** gsc compares the two
  signatures as text (ADR-0192 §D, GS0611) and binds each in its own file's
  imports, while cs2gs builds each G# file's imports and type aliases while
  translating that file — including a whole-file pre-scan of qualified
  references — so no check made while translating one file can predict the
  other file's spelling. The translator therefore only emits a pair when the
  caller sets `emitPartialMethodPairs` (default off: the implementation alone
  is emitted, exactly as before), and then only TENTATIVELY: both parts carry
  a pair key. The caller must translate the whole project through
  `PartialMethodPairReconciler.TranslateUntilStable` before printing anything
  (the cs2gs `TranslateStage` does). A pair survives only when it has exactly
  one declaring and one implementing part whose printed signatures — without
  body or method-level attributes, with parameter annotations and defaults —
  are identical. A mismatched pair's key is suppressed and every unit holding
  one of its parts is **re-translated** with the translator treating that
  method as if pairs were off, so its output is exactly the pre-amendment
  output (re-translation, not editing the printed tree, also discards any
  import or alias the dropped declaring part had recorded). The check repeats
  until no pair mismatches, since re-translating a file can change how its
  other pairs spell; a round cap suppresses every remaining pair.
- **Parameter attributes.** A pair whose two parts are in one file emits the
  union on both parts. A cross-file pair with any parameter attribute on
  either part is not emitted at all: copying one file's attribute into the
  other file can resolve it to a different type or add an import that breaks
  that file's own code, a leak the signature comparison cannot see.
- **Boundaries — the pre-amendment rule still applies** when any of these
  holds: legacy merge mode (`preservePartialParts: false`, whose single
  non-partial G# type cannot hold a partial method, GS0608); either part lives
  in a document cs2gs does not translate — outside the caller's
  `retainedFilePaths` (a project with generator references), or generated by
  the loader's own rule (under the project's `obj/`/`bin/`, or carrying the
  `<auto-generated>` header; `GeneratedSourceDetection`) — because that part is regenerated at build by
  gsgen, not translated, and gsgen does not yet emit partial-method parts
  (emitting only the hand-written half as `partial` would be GS0610); the
  method is an extension method, an explicit interface implementation,
  `extern`, a member of the hoisted entry class, or a member of a record or
  interface (no G# `partial func` spelling, GS0607); the two C# parts name a
  parameter differently (legal in C#, a GS0611 mismatch in G#).
- **Unimplemented partial methods are still elided with their call sites.** G#
  deliberately has no optional-hook elision (ADR-0192 §B, GS0609), so the
  translation layer keeps doing it.
- **Follow-on work, not done here:** having gsgen emit partial-method parts for
  generator-declared hooks (the MVVM `partial void OnXChanged(T)` +
  user-implementation shape, which today still takes the pre-amendment path)
  and retiring the `GeneratedRegex` rewrite above in favour of a real
  declaring part plus a gsgen-produced implementing part (ADR-0192 follow-on
  items 2–3, issue #4301). *Update (2026-09-25):* both are done; see the
  `GeneratedRegex` rules in §B.

## Consequences

- Positive: closes the dominant `Oahu.UI` blocker while *removing* the largest
  pieces the freeze approach required — no in-cs2gs generator driver, no
  generated-tree translation, no primary-part ordering hazard, no frozen-output
  determinism fixtures. cs2gs shrinks; the migrated project's build carries the
  weight.
- Positive: generated members stay **live and correct** — they regenerate when
  the package, the annotations, or the version source change, matching how the
  project behaves as native G#. No stale frozen snapshots.
- Positive: one code path serves native builds and migration. The gsgen fidelity
  fixes (#2209–#2211) and a G#-native `ThisAssembly` are reusable build-time
  capabilities, not migration-only translator special-cases.
- Neutral → new work moves to the build system: the cs2gs pipeline's Compile
  stage must run gsgen (§B); gsc/SDK gains `ThisAssembly` synthesis (§C); G#
  needs an assembly-attribute surface for §E if it lacks one.
- Negative: a migrated project is **not fully self-contained** — it keeps
  depending on the generator package's analyzer (and gsgen) at build time. For
  MVVM this is moot (the runtime `ObservableObject` base already ties the project
  to the package), but a "port away from all C#/NuGet" migration would want a
  freeze mode (see Scope limitation).

## Scope limitation (explicitly out of scope)

- **A self-contained "freeze" migration mode** — translating Roslyn-generator
  output into frozen, hand-editable G# so the project can shed the generator
  package entirely — is a possible opt-in but is *not* the default and not built
  here. The default is live reproduction (§A).
- **Non-reproducible generated code** — MSBuild codegen with no G# analogue, or
  generators outside gsgen's attribute-driven fidelity boundary (ADR-0145 §H) —
  is surfaced via triage (§F), not silently frozen. Closing each is its own
  gsc/SDK/gsgen item.

## Alternatives considered

- **Run source generators inside cs2gs and translate/freeze their output** (this
  ADR's original draft). Rejected: it duplicates the generator execution and
  back-translation that ADR-0145 already performs in the build, freezes
  stale snapshots that drift from the package/version source, and carries a large
  translator surface (a strip-then-run driver, a primary-part ordering fix, a
  generated-tree classification, frozen-output determinism fixtures) — nearly all
  of which the reproduce-at-build principle deletes.
- **Special-case the well-known generators** (synthesize MVVM members /
  `ThisAssembly` from templates in cs2gs). Rejected: brittle and unbounded, and
  it re-implements logic the real generator / SDK already own. §B/§C reproduce
  them generically.
- **Keep the type-declares skip gate.** Rejected: it classifies on the wrong
  axis. It correctly drops a generated `GlobalUsings.g.cs` but also silently
  drops a hand-written `AssemblyAttributes.cs`, losing real semantics. Provenance
  (§E) is the correct gate.
- **Leave `ThisAssembly` frozen (translate the obj `.cs`).** Rejected: the
  constants go stale every commit, and a build-native synthesis (§C) — following
  the ADR-0142 resx precedent — keeps them correct with no migration-time work.
