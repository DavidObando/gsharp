# Release version-bump checklist

This page lists every place a G# release version lives, which of them must
follow the latest published release, and what to edit when a release ships.
[`build/check-release-version-refs.py`](../../build/check-release-version-refs.py)
enforces it. The check runs on every pull request in the `release-version-refs` job of
[`build.yml`](../../.github/workflows/build.yml). It reads the checkout only and
never builds, packs or publishes anything.

```sh
python3 build/check-release-version-refs.py        # the check itself
python3 build/test-check-release-version-refs.py   # proves each part can fail
```

## Source of truth

**`website/src/data/release.json` `version`** is the latest published release.
The website renders it, `website/scripts/prepare-showcase.py` names the
downloads after it, and the `website/tests/verify-*.py` checks restore that
exact version from nuget.org.

The newest `v*` Git tag is deliberately not the source of truth. A tag is
pushed and published first; `release.json` can only follow in a later PR,
because the website verifiers fail until the package is on nuget.org. During
that window the tag is newer than every reference, and a tag-based check would
fail on every open PR.

The product version itself is not hand-edited. Nerdbank.GitVersioning derives
it as `<version.json base>.<git height>`. Every commit on `main` increments the
height by one (the history is linear because PRs are squash-merged). The
`Show Nerdbank.GitVersioning version` step in `build.yml` prints it.

The check also sweeps every tracked text file for a package-qualified pin
(`Gsharp.NET.Sdk/X`, `Gsharp.Templates::X`, `"Gsharp.NET.Sdk": "X"`,
`--version X`, `Include="Gsharp.Repl" Version="X"`, nuget.org flat-container
paths) for any of the published package ids. A pin to a version other than the
release fails unless it is allow-listed.

### Historical evidence (hash-checked, not relabeled)

`HISTORICAL_FILES` in the checker pins the original 0.4.591 Trail and concurrency
archives, Trail editor images and capture JSON by SHA-256 (canonical LF for JSON).
Missing or changed evidence fails, as does an unknown versioned archive. The
capture's application SDK, VS Code extension and .NET SDK are independent
historical facts, not references to the current release. Keep the historical
disclosure visible and independently execute new examples/downloads. A new
capture, if made, needs its own authentic provenance; never update old metadata
to imply the pixels show a newer toolchain.

### Intentionally not the latest release (allow-listed)

Each allow-list entry names a path, the exact version(s) and the reason.
Paths are `fnmatch` globs exactly as written in `ALLOWED`, where `*` also
matches `/` (so `website/versioned_docs/*` covers every file below it). An
entry that no longer matches anything fails the check, so the list cannot rot.

| Path | Version | Why it stays |
|---|---|---|
| `website/versioned_docs/*` | any | Released snapshots keep their own release's commands. The default snapshot's release-facing references are checked separately (above). |
| `src/vs-gsharp/templates/Project/*` | 0.3.159 | Placeholder. `BuildGSharpTemplates` in `src/vs-gsharp/src/VsGsharp/VsGsharp.csproj` overwrites the `Sdk` attribute with `Gsharp.NET.Sdk/$(NuGetPackageVersion)` when it builds the VSIX. |

### Derived by the build (never hand-edited)

| Where | Value | Source |
|---|---|---|
| NuGet packages `Gsharp.NET.Sdk`, `Gsharp.Templates`, `Gsharp.Repl`, `Gsharp.Gsfmt`, `Gsharp.Cs2Gs`, `GSharp.CodeAnalysis.Analyzers.Testing` | `NuGetPackageVersion` | Nerdbank.GitVersioning. Packed into `out/bin/Release/nupkgs` by `build/gsharp.build.props` `PackageOutputPath`. |

## Patch release in the same line (0.4.N to 0.4.M)

Order matters: publish first, then point the website at the published package.

1. Tag and publish the release: push tag `vM` on the commit whose
   `build.yml` run printed `M`. The `publish-*` jobs in `build.yml` do the
   rest, one job per destination (ADR-0218); the GitHub release stays a draft
   until `publish-finalize` finds the version on every destination. The
   release runbook (`docs/release/final-csharp-release.md`, which lands in a
   separate PR) covers the
   secrets and verification in detail. Confirm every package is on nuget.org
   at `M` before step 2.
2. In one post-publish PR:
   1. `website/src/data/release.json`: set `version` to `M` and `tag` to `vM`.
   2. Update every "must equal" row above that does not regenerate itself:
      `install.md`, `trail.md`, `release-notes.md` ("Reading these notes"),
      `sdk-projects.md`, `docs-authoring.md`, `website/README.md`, both sample
      `.gsproj` files, `samples/ConcurrencyPatterns/README.md` and
      `docs/sdk-usage.md`.
   3. Refresh the default docs snapshot from the actual published tag.
      See "Refreshing a docs snapshot" below.
   4. Regenerate the downloads: `python3 website/scripts/prepare-showcase.py`
      writes `trail-M.zip` and `concurrency-patterns-M.zip`. Retain historical
      downloads and register their original hashes when they become historical.
      ZIP creator OS, relative POSIX ordering and LF payloads must be deterministic.
      Store payloads without compression so zlib-version differences cannot
      change the archive hash.
   5. Regenerate the concurrency evidence:
      `python3 website/tests/verify-concurrency-patterns.py --race`. It needs Go
      and restores `Gsharp.NET.Sdk/M` from nuget.org. It rewrites
      `website/static/data/concurrency-checks.json` with `sdkVersion` and the
      new bundle's `bundleSha256`; commit that file.
   6. Preserve authentic historical editor captures and their explicit
      historical disclosure. Report independently executed current-release
      examples separately; do not claim a new capture without actually making one.
   7. Run `python3 build/check-release-version-refs.py`, then build and test
      the site (`CONTRIBUTING.md`, "Documentation site"; also
      `npm run test:content`, `python3 website/tests/verify-examples.py` and
      `python3 website/tests/verify-trail.py`).

## Bootstrap pin move (`global.json` `msbuild-sdks`)

The repository is built by the pinned `Gsharp.NET.Sdk` (currently `0.5.212`),
whose emitter dropped annotations on `shared` fields before the fix in #4911 (issue
#4903). `0.5.7` contains #4911, and the `ThreadLocal<T>` workarounds that
stood in for `@ThreadStatic` fields under the older pin have been reverted
(issue #4909):

- `src/Core/CodeAnalysis/Binding/DeclarationBinder.Functions.gs`
  (`conformanceMatchingDepth`);
- `src/Sdk/Gsharp.Runtime.Channels/SelectWaiter.gs` (`cache`),
  `SelectRandom.gs` and `InlineBudget.gs`.

`Issue4909ConformanceDepthThreadIsolationTests` (Core.Tests) and
`Issue4909ThreadStaticStateTests` (Runtime.Channels.Tests) fail if a pin moves
to an SDK whose emitter drops `@ThreadStatic` on these fields again.

The pinned `gsc` compiles the packed `tools/task/Gsharp.NET.Sdk.dll`, as it
compiles every other repository project (the N-1 rule in `CONTRIBUTING.md`). A
codegen correction for the task assembly therefore ships one release after the
release that contains it (issues #4921 and #5413). The `build` job's
`build/check-netstandard-host-refs.py` step fails if the packed task assembly
names a `System.Private.*` host assembly, and `build/check-netstandard-member-refs.py`
fails if any of its TypeRefs or MemberRefs is missing from the netstandard2.0
reference surface (issue #4924). The `desktop-msbuild-sdk-smoke` job builds a
project with Visual Studio's MSBuild against the package from the same build, and
`publish` depends on it, so a task assembly that .NET Framework cannot load or run
blocks the release.

## Minor release (0.N to 0.N+1)

Everything in the patch procedure, plus:

1. **Before** the first release of the new line: set `version.json` `version`
   to the new base (for example `"0.5"`) on `main`. The height restarts, and
   assembly versions change to `0.N+1.0.0`. For 0.5 this belongs in the
   separate version-bump PR that follows the cut-over (the 0.5 bump PR, #4902). After the final 0.4.x tag, `main` must not produce more
   `0.4.*` versions, because they would collide with security-fix releases
   from the C# branch. Check the first build's printed version.
2. After publishing, cut a new docs snapshot from the actual release tag
   instead of refreshing an older line. Follow "Refreshing a docs snapshot"
   below; the tag's sidebar supplies the snapshot navigation too.
3. `release.json` `docsVersion` becomes `0.N+1`. The previous snapshot's
   references become historical and fall under the `website/versioned_docs/*`
   allow-list entry.
4. Release notes: rename the "Unreleased" heading to the new release and
   start a new empty "Unreleased" section. The heading has to be written
   before the release commit exists. With `main` frozen, a squash merge
   becomes the next commit, so the release number is the
   `nbgv get-version -v SimpleVersion origin/main` plus one in the patch
   number. Check
   it against the merged commit's printed version before tagging.

### The 0.5 website cut

The 0.5 website cut targets published v0.5.199, not unreleased main.
`release.json` names `0.5.199`/`v0.5.199` with `docsVersion` `0.5`;
`versions.json` is `["0.5","0.4","0.3"]`. Its 51 source pages and sidebar
come from that tag, with reviewed editorial corrections and updated release
pointers. The 0.4/0.3 snapshots and original archives remain historical.

The docusaurus config needs no change: it takes versions from `versions.json`.
Content/browser tests cover the default release, older snapshots and Next;
check version-dropdown, navigation and search filters after each cut.

## Refreshing a docs snapshot

Placeholders in this section: `DOCS_VERSION` is the docs snapshot name
(`release.json` `docsVersion`, e.g. `0.4`), and `RELEASE_VERSION` is the
published release (`release.json` `version`, e.g. `0.4.1130`).

`npm run docusaurus docs:version DOCS_VERSION` refuses a version that
`versions.json` already lists ("this version already exists"). It also copies
into an existing directory without deleting files that are already there.

Extract `website/docs` and `website/sidebars.ts` from the actual
`vRELEASE_VERSION` Git tag into a named checkout-local work directory.
Populate `versioned_docs/version-DOCS_VERSION` from those source pages and
derive its sidebar JSON from the tag's sidebar. Remove stale pages in the
snapshot being refreshed, not in other versions. Add/prepend the snapshot
name in `versions.json`. Docusaurus's version command can scaffold the
directory, but its copy of current `website/docs` is not release provenance.

The tag's docs can still name the previous website release because
publication precedes the docs PR. Update those release pointers and apply
reviewed editorial corrections, checking compiler/runtime APIs against the
tag. Preserve post-tag content in Next and all original release-note bullets;
do not silently copy newer features into the released snapshot.

Then:

- Write the snapshot's release-notes heading with the exact version/date,
  tag, source commit and published feature boundary. Keep newer release
  bullets in Next.
- Update the "snapshot is based on/refreshed from `vRELEASE_VERSION`" sentences in
  `docs/docs-authoring.md` and `website/README.md`.
- Run `npm run test:content`. It checks the snapshot's install page, Trail
  download link, descriptions, diagnostic catalogue and legacy anchors.
