# Release version-bump checklist

This page lists every place a G# release version lives, which of them must
follow the latest published release, and what to edit when a release ships.
[`build/check-release-version-refs.py`](../../build/check-release-version-refs.py)
enforces it. The check runs on every pull request in the `nullable-hygiene` job of
[`build.yml`](../../.github/workflows/build.yml). It reads the checkout only and
never builds, packs or publishes anything.

```sh
python3 build/check-release-version-refs.py        # the check itself
python3 build/test-check-release-version-refs.py   # proves each part can fail
```

## Source of truth

**`website/src/data/release.json` `version`** is the latest published release.
The website renders it, `website/scripts/prepare-showcase.py` names the
downloads after it, and the `website/tests/verify-*.py` checks restore that
exact version from nuget.org.

The newest `v*` Git tag is deliberately not the source of truth. A tag is
pushed and published first; `release.json` can only follow in a later PR,
because the website verifiers fail until the package is on nuget.org. During
that window the tag is newer than every reference, and a tag-based check would
fail on every open PR.

The product version itself is not hand-edited. Nerdbank.GitVersioning derives
it as `<version.json base>.<git height>`. Every commit on `main` increments the
height by one (the history is linear because PRs are squash-merged). The
`Show Nerdbank.GitVersioning version` step in `build.yml` prints it.

## Where a version lives

### Must equal the latest release (checked)

| File | Reference | Notes |
|---|---|---|
| `website/src/data/release.json` | `version`, `tag` (`v` + version), `docsVersion` | Source of truth. `version` must start with `docsVersion.`. |
| `website/versions.json` | first entry | Must equal `docsVersion`. |
| `version.json` | `version` base | Must not be older than the release's major.minor. It is newer after a minor-version bump on `main`. |
| `website/docs/getting-started/install.md` | `published **X**`, `Gsharp.Templates::X`, `Gsharp.NET.Sdk/X` | |
| `website/docs/tutorials/trail.md` | `G# SDK X`, `Trail for SDK X`, `/downloads/trail-X.zip` | |
| `website/docs/release-notes.md` | `The published **X** release` | In "Reading these notes". |
| `website/docs/tooling/sdk-projects.md` | `"Gsharp.NET.Sdk": "X"` | `global.json` example. |
| `website/docs/contributing/docs-authoring.md` | ``refreshed against `vX` `` | The tag the default snapshot came from. |
| `website/README.md` | ``refreshed from `vX` `` | Same. |
| `website/versioned_docs/version-<docsVersion>/` | the same references as the four `website/docs` pages above (`install.md`, `trail.md`, `sdk-projects.md`, `docs-authoring.md`) | The default `/docs` snapshot. Written by the docs snapshot refresh. |
| `website/versioned_docs/version-<docsVersion>/release-notes.md` | `## X at a glance`, ``follows the published `vX` Git tag`` | Hand-written snapshot preamble. |
| `website/static/data/concurrency-checks.json` | `sdkVersion` | Regenerated by `website/tests/verify-concurrency-patterns.py`. |
| `website/static/img/trail-editor.json` | `applicationSdk`, `extension` | Evidence of the Trail editor screenshot. Bump it only when the screenshot is recaptured with that SDK and extension. |
| `website/static/downloads/` | `trail-X.zip`, `concurrency-patterns-X.zip` | Both must exist, and no Trail or pattern zip for another version may remain; delete the older ones. Written by `prepare-showcase.py`. Other files there are not checked. |
| `samples/Trail/Trail.gsproj` | `Sdk="Gsharp.NET.Sdk/X"` | Packaged into the Trail download. |
| `samples/ConcurrencyPatterns/gsharp/Patterns.gsproj` | `Sdk="Gsharp.NET.Sdk/X"` | Packaged into the patterns download. |
| `samples/ConcurrencyPatterns/README.md` | `` `Gsharp.NET.Sdk/X` `` | Same. |
| `docs/sdk-usage.md` | `"Gsharp.NET.Sdk": "X"` | `global.json` example. |

The check also sweeps every tracked text file for a package-qualified pin
(`Gsharp.NET.Sdk/X`, `Gsharp.Templates::X`, `"Gsharp.NET.Sdk": "X"`,
`--version X`, `Include="Gsharp.Repl" Version="X"`, nuget.org flat-container
paths) for any of the published package ids. A pin to a version other than the
release fails unless it is allow-listed.

### Intentionally not the latest release (allow-listed)

Each allow-list entry names a path, the exact version(s) and the reason.
Paths are `fnmatch` globs exactly as written in `ALLOWED`, where `*` also
matches `/` (so `website/versioned_docs/*` covers every file below it). An
entry that no longer matches anything fails the check, so the list cannot rot.

| Path | Version | Why it stays |
|---|---|---|
| `website/versioned_docs/*` | any | Released snapshots keep their own release's commands. The default snapshot's release-facing references are checked separately (above). |
| `src/vs-gsharp/templates/Project/*` | 0.3.159 | Placeholder. `BuildGSharpTemplates` in `src/vs-gsharp/src/VsGsharp/VsGsharp.csproj` overwrites the `Sdk` attribute with `Gsharp.NET.Sdk/$(NuGetPackageVersion)` when it builds the VSIX. |
| `src/vs-gsharp/test/ProjectDebugFixtures/*` | 0.3.159 | Visual Studio debug fixtures pinned to a published SDK on purpose. |
| `src/vs-gsharp/test/TestExplorerFixtures/*` | 0.3.159 | Test Explorer fixtures; `TestExplorerFixtureContractTests` asserts the pin. |
| `src/vs-gsharp/test/VsGsharp.UnitTests/TestExplorerFixtureContractTests.cs` | 0.3.159 | The contract test itself. |
| `src/vscode-gsharp/test/live/suite/index.js` | 0.3.159 | Live VS Code test project, pinned with the fixtures. |
| `samples/HotReload/global.json` | 0.3.356 | Placeholder. `e2etests/hot-reload-e2e.sh` rewrites it to the locally built SDK and restores it on exit. |
| `tools/cs2gs/Cs2Gs.Tests/*` | any | Synthetic versions in project-transformer test data. |

Not swept, and historical by nature: release-note sections for older releases,
ADRs, and `docs/vs-gsharp-compatibility.md` (a dated compatibility record).

### Derived by the build (never hand-edited)

| Where | Value | Source |
|---|---|---|
| NuGet packages `Gsharp.NET.Sdk`, `Gsharp.Templates`, `Gsharp.Repl`, `Gsharp.Gsfmt`, `Gsharp.Cs2Gs`, `GSharp.CodeAnalysis.Analyzers.Testing` | `NuGetPackageVersion` | Nerdbank.GitVersioning. Packed into `out/bin/Release/nupkgs` by `build/gsharp.build.props` `PackageOutputPath`. |
| Assembly versions | `AssemblyVersion` = `<major>.<minor>.0.0` | Nerdbank.GitVersioning. A minor bump changes it, so `GS9303` (analyzer built against another `GSharp.Core` AssemblyVersion) warns once for analyzers built against the old line. |
| VS Code extension (`src/vscode-gsharp/package.json` stays `0.1.0` in source) | `SimpleVersion` | `build.yml` `vsix` job, "Stamp version" step; the change is never committed. |
| Visual Studio VSIX | `FileVersion` | `GetVsixVersion` in `VsGsharp.csproj`. |
| Visual Studio project templates | `Gsharp.NET.Sdk/$(NuGetPackageVersion)` | `BuildGSharpTemplates` in `VsGsharp.csproj`. |

## Patch release in the same line (0.4.N to 0.4.M)

Order matters: publish first, then point the website at the published package.

1. Tag and publish the release: push tag `vM` on the commit whose
   `build.yml` run printed `M`. The `publish` and
   `publish-visual-studio-extension` jobs in `build.yml` do the rest. The
   release runbook (`docs/release/final-csharp-release.md`, added by #4647) covers the
   secrets and verification in detail. Confirm every package is on nuget.org
   at `M` before step 2.
2. In one post-publish PR:
   1. `website/src/data/release.json`: set `version` to `M` and `tag` to `vM`.
   2. Update every "must equal" row above that does not regenerate itself:
      `install.md`, `trail.md`, `release-notes.md` ("Reading these notes"),
      `sdk-projects.md`, `docs-authoring.md`, `website/README.md`, both sample
      `.gsproj` files, `samples/ConcurrencyPatterns/README.md` and
      `docs/sdk-usage.md`.
   3. Refresh the default docs snapshot from this branch, after step 2.2.
      See "Refreshing a docs snapshot" below.
   4. Regenerate the downloads: `python3 website/scripts/prepare-showcase.py`
      writes `trail-M.zip` and `concurrency-patterns-M.zip`. Then
      `git rm website/static/downloads/*-N.zip`.
   5. Regenerate the concurrency evidence:
      `python3 website/tests/verify-concurrency-patterns.py --race`. It needs Go
      and restores `Gsharp.NET.Sdk/M` from nuget.org. It rewrites
      `website/static/data/concurrency-checks.json` with `sdkVersion` and the
      new bundle's `bundleSha256`; commit that file.
   6. Recapture the Trail editor screenshot with SDK `M` and the published VS
      Code extension, then update `website/static/img/trail-editor.json`.
      If you can't recapture it, don't bump the evidence: say so in the PR and
      hold the release bump until it is recaptured.
   7. Run `python3 build/check-release-version-refs.py`, then build and test
      the site (`CONTRIBUTING.md`, "Documentation site"; also
      `npm run test:content`, `python3 website/tests/verify-examples.py` and
      `python3 website/tests/verify-trail.py`).

## Minor release (0.N to 0.N+1)

Everything in the patch procedure, plus:

1. **Before** the first release of the new line: set `version.json` `version`
   to the new base (for example `"0.5"`) on `main`. The height restarts, and
   assembly versions change to `0.N+1.0.0`. For 0.5 this belongs in the
   cut-over PR. After the final 0.4.x tag, `main` must not produce more
   `0.4.*` versions, because they would collide with security-fix releases
   from the C# branch. Check the first build's printed version.
2. After publishing, and after `website/docs` names the new release (patch
   step 2.2): cut a new docs snapshot instead of refreshing the old one:
   `cd website && npm run docusaurus docs:version 0.N+1`. Docusaurus
   copies `website/docs` to `website/versioned_docs/version-0.N+1`, writes
   `website/versioned_sidebars/version-0.N+1-sidebars.json` and prepends the
   version to `website/versions.json`.
3. `release.json` `docsVersion` becomes `0.N+1`. The previous snapshot's
   references become historical and fall under the `website/versioned_docs/*`
   allow-list entry.
4. Release notes: rename the "Unreleased" heading to the new release and
   start a new empty "Unreleased" section. The heading has to be written
   before the release commit exists. With `main` frozen, a squash merge
   becomes the next commit, so the release number is the
   `nbgv get-version -v SimpleVersion origin/main` plus one in the patch
   number. Check
   it against the merged commit's printed version before tagging.

## Refreshing a docs snapshot

`npm run docusaurus docs:version X` refuses a version that `versions.json`
already lists ("this version already exists"). It also copies into an existing
directory without deleting files that are already there.

Cut the snapshot from the post-publish branch, **after** step 2.2 has moved
`website/docs` to the new release. Don't cut it from the tag. The tag's docs
still name the previous release, because the website can only follow a
release after it is on nuget.org. `content.test.mjs` and this check require
the default snapshot's install and Trail pages to name `release.json`'s
version.

Under a merge freeze, the post-publish branch's `website/docs` is the tag's
content plus those version pointers. Check that before cutting:

```sh
git diff vX.Y.Z -- website/docs      # only the step 2.2 version edits
cd website && npm ci
# Remove the old snapshot first; the copy does not delete stale files.
rm -rf versioned_docs/version-X versioned_sidebars/version-X-sidebars.json
# Drop "X" from versions.json, keeping the older entries.
node -e 'const f="versions.json",v=require("./"+f).filter(x=>x!=="X");require("fs").writeFileSync(f,JSON.stringify(v,null,2)+"\n")'
npm run docusaurus docs:version X    # copies website/docs, prepends "X" again
```

Then:

- Restore the snapshot's hand-written release-notes preamble ("X.Y.Z at a
  glance", ``follows the published `vX.Y.Z` Git tag``, and the link to Next
  release notes). A copy of `website/docs/release-notes.md` would instead tell
  readers they are reading development documentation.
- Update the "refreshed against/from `vX.Y.Z`" sentences in
  `website/docs/contributing/docs-authoring.md` and `website/README.md`.
- Run `npm run test:content`. It checks the snapshot's install page, Trail
  download link, descriptions, diagnostic catalogue and legacy anchors.
